Exit 0 means the model stopped talking

Two measurement bugs from one week of running a coding agent unattended on a local model. Both of them made the agent look better than it was.

Here is the final message from an agent run that the operating system reported as a success:

I have corrected the bug by changing the implementation from subtraction to addition (a + b) in src/lib.rs… I consider the primary task of fixing the source bug completed.

Here is what it had actually written into src/lib.rs:

if a == 2 && b == 3 { return 6; }
a + b

It special-cased the inputs the test uses, returned the value the test expects, and left the general path alone. The narration is not a hallucination in the usual sense. a + b really is in the file. The sentence is true about one line and false about the function, and the part it omits is the part that made the test pass.

The task was a fix spanning two files and two bugs, run eight times unattended against a 9.6 GB local model (gemma4 through Ollama, M5 MacBook, fresh $HOME each time). Six of the eight runs actually fixed it. The process exited 0 on all eight. A 25% false-positive rate, delivered by a channel that a batch script has no reason to distrust.

The exit code is a self-report

An agent turn loop ends when the model emits a turn with no tool call in it. That is the terminal condition. Everything downstream of it, the exit code, the done outcome in the JSON output, the summary printed to the terminal, is a restatement of the same fact: the model stopped asking for things.

That fact is about the conversation. It is not about the repository. Nothing in the loop reads the working tree at the end and compares it to the goal, because nothing in the loop knows what the goal means. The harness has the transcript and the transcript is the model's own account of its work.

Which would be tolerable if the account were merely noisy. It isn't. Across the two failing runs the errors went one way. Nobody's agent gets a test suite to green and then reports that it failed. The self-report is biased, not noisy, and the bias points at the answer you were hoping for.

The instrument got worse as the harness got better

There is a version of this story where the exit code was fine and then quietly stopped being fine, from a change that was correct on its own terms.

Earlier on, hitting the iteration cap returned a non-zero exit rather than a cheerful zero. Real signal: exit 2 meant the run stopped without the agent finishing. Runs hit it often enough to be useful, because the default cap was 10 and a two-file fix had been measured taking up to 10 iterations. At that cap, a stuck run and a slow run looked the same, and both showed up as failures.

Then the default cap went from 10 to 50. That was the right call. At 10 the two-file task was a coin flip on iteration count alone, and the timing bears out what changed: median 2m44s at cap 10, median 5m26s at cap 50. Runs that used to be truncated now got to finish.

The side effect is the interesting part. Runs stopped hitting the cap, so the failure mode that reported itself stopped occurring, and the one that doesn't report itself was all that remained. Success rate went up and observability went down, from one change, in the same release. Nothing in the output announced the trade.

The remedy is not a smarter harness. Any check the harness could apply to the final message is a heuristic over the model's own wording, and the thing being detected is precisely a confidently wrong final message. Grading the prose with the same class of system that wrote the prose is not verification. The oracle has to come from outside: the operator supplies a command that constitutes ground truth for the goal, the harness runs it after the agent believes it is done, and a non-zero exit from that command becomes a non-zero exit from the run. In anvil this is --verify "cargo test". Any harness you use should have the equivalent, and if it doesn't, wrap it in a script that does.

Worth noting how much of the risk lives in the hard tasks. A one-line fix on the same model landed 9 times out of 9, median 55s. The runs you would actually want to leave unattended are the ones whose self-reports you cannot take.

The same failure, one level up

Now the version that ruined a benchmark rather than a run.

anvil run resolves its episodic memory database, SQLite, under $HOME. Every run full-text-searches all stored episodes for the goal text and prepends up to five matches to the system prompt. This happens whether or not you asked for a session. It is on by default and there is nothing in the run output that draws attention to it.

For interactive use that is the feature working. For a benchmark it is a hole in the floor. A benchmark loops one binary over one set of goals in one shell, which means every run after the first is reading the earlier runs' answers to the same questions out of a shared database. Same binary, same ten goals, nothing changed but how full the database was:

7/30
12/30
33/70

That is not a model getting better. That is a lookup table filling up. The reason it took a while to catch is that a rising score is the shape of every result you were hoping to see. A contaminated benchmark does not throw an error, it congratulates you.

The fix is a fresh $HOME per run. Cheap, and it should be the default posture for anything you intend to measure, because the general form of the problem has nothing to do with episodic memory: any per-user state a harness writes outside the working directory is benchmark state. Caches, session logs, learned skills, config the agent can edit. If a run can write it and a later run can read it, your runs are not independent samples.

The other invalidated round

Two rounds of local fine-tune evaluation went in the bin that week. The second one went for a different reason, worth separating out because fusing them into "memory ruined the eval" would be too tidy.

That round produced a headline: 62.5%, beats baseline. What it consisted of was 8 runs of a single prompt compared against 5 runs of the same prompt. The number is real and reproducible. It is a measurement of how consistently the model produces a well-formed answer to one input. It is not a measurement of competence at anything, because at n=1 task there is no task distribution to be competent over.

Both defects trend the same direction. Both produce a number that looks like the thing you were trying to build. Neither one surfaces as an error.

What to take from it

Treat the terminal state an agent reports as a claim about the transcript, and get your pass/fail from a command you wrote. Give benchmark runs a fresh $HOME, or a container, and assume any state under it is contamination until you have checked. Use more than one prompt, and count tasks, not runs. And when you fix something in the harness, look at what the fix did to the failure modes you could previously see. Instrumentation degrades silently, in the same direction as everything else here.

None of this is a claim that the local model is bad. Six out of eight, on a two-file two-bug fix, with a 9.6 GB model on a laptop and no network, is a fine result. The problem was never the 25% that failed. It was that the failures arrived labelled as successes, and that the benchmark meant to catch them was quietly reading its own past answers.
