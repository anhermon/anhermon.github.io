Telemetry: MCP tool calls as OTel spans

MONITORING
2026-07-28 08:14 UTC

MCP servers don't expose OpenTelemetry spans on their own, so a slow or failing tool call is normally invisible unless tracing code is added inside the server itself. mcp-trace sits between an MCP client and an MCP server, changes nothing about the protocol, and emits one OTel span per JSON-RPC tools/call.

Source: docs/img/demo.cast in anhermon/mcp-trace, a public asciinema recording of the project's own demo, made 2026-07-28. Every start time, duration and error flag below is read straight out of that recording's span started / span ended log lines. No waterfall: each trace here is exactly one span, with no parent-child nesting to draw — the last span was still in flight when the recording stopped and is drawn open-ended.

Evals: when the exit code lies

An agent that exits 0 and reports done isn't necessarily telling the truth, and a harness that grades its own work can't be trusted to catch the difference.

Source
the Gate numbers are from anhermon/anvil's own run logs. The Arena numbers are from a harness-comparison tool built for exactly this measurement, harness-arena, not yet public.
Gate
9 runs of a local agent harness (gemma4 over Ollama) against a real bug in a Rust CLI, 2026-07-30. Task A: single easy warm-up. Task B: same harder bug-fix prompt, run 8 times. Two independent checks run after the harness reports done — neither influenced by its own exit code: a held-out test file, and a byte-diff of the in-repo test file to catch whether it edited tests it was told to leave alone.
Arena
120 recorded runs across harness·model combinations, 25–26 July 2026, 118 with usable data. Status is completion, not quality — only 21 cells were ever human-graded.

Hover or tab a row for its detail.

The finding: the harness exited 0 and reported outcome=done on every one of the 8 runs of the harder task. The held-out test disagreed twice. A cron loop built on that exit code would have recorded 8 successes and shipped 2 broken repos. The fix is not a better model — it's moving the pass/fail decision outside the thing being graded. Half of those 8 runs also edited the test file they were explicitly told not to touch, including one that still failed the held-out check anyway: instruction- following and actually-fixing-the-bug are two separate failures here, not one.

Identified

Fleet observability: token waste, tool coverage, model routing — across 990 real sessions

At fleet scale the question isn't whether one agent is working, it's whether a given run wasted tokens re-reading a file, whether it got routed to a model with real evidence behind that choice, and whether its tool usage looked like the runs that finished versus the ones that didn't — none of that is visible from a transcript scrollback.

  1. How this is collected

    session-usage-audit parses every stored Claude Code transcript directly — every message, every tool call, every subagent fork's real token cost joined from its completion event, not its launch acknowledgment. The routing knowledge base is queried live over its MCP server, not a cached export. Run just now: 198,779 lines across 1,859 transcript files, 990 sessions, 2026-06-06 through 2026-08-01.

  2. Token waste

    12.18 billion cache-read tokens across those 990 sessions. This exact session — the one that built this page — is the single largest: 2,386,582,640 tokens, 19.6% of the account's entire 90-day cache-read volume. 2,729 of 6,128 Read calls (44.5%) re-read a file already read earlier in the same session. The costliest single pattern is one subagent per list item instead of one agent for the whole list — this session did that 7 times for 3,500,017 tokens.

  3. Missing tools

    The routing knowledge base's own MCP server implements 12 tools; only 6 are exposed in this session, including a gap in workflow_digest — the cheap fleet-status check its own documentation says to call first.

  4. Model selection, caught live

    Querying the routing knowledge base live, right now, to write this section surfaced a second finding: this page previously stated docs-explain's best routing evidence at n=4. The live answer today is different — zero non-stale rows, one entry aged out, recommend_delegation now returns "no evidence for docs-explain" rather than a recommendation. The stale number was caught and corrected before it shipped, by treating "is this still true" as a live question instead of trusting the last write.

Multi-tenant event ingestion: two tenants, one fixture set

A multi-tenant system can leak data across tenants in ways that look fine in a naive test, because both tenants still get plausible-looking results back.

Source
anhermon/event-ingest-platform (private: ask and I'll grant access), Java/Spring Boot, Postgres row-level security per tenant. Every figure below is a real HTTP response from a freshly created stack.
The setup
two tenants replay the identical Slack fixture set, including messages from the same person at the same address. Acme allows message and reaction_added, Gmail enabled. Globex allows message only, no Gmail. Any missing filter or leaked row shows up immediately as a number that should not match, matching.
same fixtures into both tenants · queried through the real API with a per-tenant bearer token

Globex: canonicalEvents3

Scenario worth pausing on: Acme's payload, correctly signed with Globex's own secret, posted to Globex's endpoint → 403 different workspace. A valid signature on the correct endpoint is not sufficient — the payload's workspace id must also belong to the tenant that owns the endpoint. angel@example.com resolves to two unrelated actors, one per tenant, same fixtures, same person, two rows: a missing tenant predicate would silently merge them, and nothing else in the system would complain.

Langfuse Ingestion Write-Mode Bug Fix

MITIGATED
2026-08-01 UTC
Problem Found
Langfuse v4's ingestion API silently rejected legacy trace-create / observation-create events unless LANGFUSE_MIGRATION_V4_WRITE_MODE was set away from default (events_only). Setting write-mode to legacy fixed that rejection but broke LANGFUSE_MIGRATION_V4_NATIVE_OTEL_BEHAVIOUR=direct (which requires dual or events_only), crash-looping langfuse-worker on a config-validation error. The ingest script kept reporting "ingested N events" success because HTTP endpoints queued events without worker drainage into ClickHouse.
Fix Applied
Configured LANGFUSE_MIGRATION_V4_WRITE_MODE=dual in the environment, satisfying both legacy event ingestion and direct OTel behavior validation rules simultaneously.
Verification
0 / 0 / 22 → 12 / 8074 / 26
Direct ClickHouse query confirmed traces / observations / scores counts jumped immediately once worker processing stabilized.

Langfuse OOM Misdiagnosis & Memory Limit Fix

MITIGATED
2026-08-01 UTC
Problem Found
langfuse-web restarted 52 times. Standard application crash-loop was suspected, but docker logs showed clean boots with no stack trace or error. docker inspect revealed Memory=0 (unbounded), unlike ClickHouse, MinIO, and Redis in the same stack. The VM console log (~/Library/Containers/com.docker.docker/Data/log/vm/console.log) confirmed Linux kernel oom-kills targeted the unbounded Node process during host memory pressure spikes.
Fix Applied
Added mem_limit: 1024m to both langfuse-web and langfuse-worker in docker-compose.yml to bound process memory explicitly alongside back-end dependencies.
Verification
52 restarts stopped
Process restarts ceased completely after applying container memory limits; continuous execution verified under host memory load.

dedup-proxy distinctBy In-Batch Duplicate Bug Fix

MITIGATED
2026-07-31 UTC
Problem Found
Initial version of dedup-proxy filtered forwarded events by eventId in newIds (membership, not occurrence), so an in-batch duplicate event ID matched the set and got forwarded twice to Langfuse.
Fix Applied
Deduplicated batch in-memory prior to forwarding check using events.distinctBy { it.eventId }.filter { it.eventId in newIds }.
Verification

Integration test (DedupIntegrationTest via ./gradlew test on apache/kafka-native:4.2.1 & postgres:18-alpine) caught the bug and verified the fix.

Pipeline Correctness-at-Volume Invariant

MITIGATED
2026-07-31 UTC
Problem Found
Aggregation pipelines looking correct at low volume can silently drop, duplicate, or fall behind once high volume hits under host contention.
Fix Applied
Implemented single Postgres transaction dedup (INSERT ... ON CONFLICT (event_id) DO NOTHING RETURNING event_id) with Kafka offset commit strictly post-transaction.
Verification
3,586,900 events verified

Kubernetes: Scaling on Consumer Lag via KEDA

Problem Found
CPU-based autoscalers fail on I/O-bound bottlenecks: consumers fall behind their topic while sitting at low CPU because the bottleneck is Postgres batch upserts.
Fix Applied
Deployed KEDA ScaledObject querying Kafka broker lag (lagThreshold: 50, maxReplicaCount: 6) to drive HPA scaling on consumer queue length instead of CPU utilization.
Partial Status
1 → 3 aggregator pods Running in 17 seconds verified (lag 0 → 156 at 08:31:52; pods sd8zf and 42bzc Running by 08:31:54). Scale-down was never captured: the watch stream died at 08:32:55 UTC (http2: client connection lost) under host contention with the second pair of pods still in ContainerCreating. maxReplicaCount was lowered 6 → 3 in response to host contention, but that mitigation has NOT been re-verified under load.

None — structural prompt guardrails and harness-level loop controls have not yet been implemented to prevent subagent branching per item.
